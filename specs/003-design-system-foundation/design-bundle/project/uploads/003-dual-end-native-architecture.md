# ADR 003 v4: 双端业务架构 + 单 app 单用户单角色（V1）

> **Status**: Accepted · **Date**: 2026-04-24（v1）· **Updated 2026-04-25 (v2)** 单 app + 角色切换 + MSB 教练端事实 · **Updated 2026-04-26 (v3)** 多角色单用户 V1 支持（议题 4 决议） · **Updated 2026-04-27 (v4)** **反转 v3 议题 4**——V1 简化为单角色（注册时锁死），多角色推迟到 V1.5+

## 一句话

MeetPR 是**双端业务**（教练 + 学员，都是一等公民），通过**单 iOS app + 单用户单角色**（V1）实现。一个 binary、一个 App Store listing、一份共享代码库；**V1 注册时选定教练 OR 学员后不可切换**，多角色（同账号同时持教练 + 学员）推迟到 V1.5+，触发条件参见 v4 changelog。

## 背景（Context）

### v1 假设（2026-04-24）

发现 [[../competitors/my-strength-book|MSB]] 被长期误读为"教练-学员协作平台"，但**当时认为它没有教练端**——教练通过外部工具编写训练计划，与学员通过微信沟通。

### v2 修正（2026-04-25 office hours v0.3）

**MSB 实际上有教练端**——但**中文市场不可达**：
- MSB 教练端存在（David 在 office hours 期间确认得知，但接触不到）
- MSB 整体产品**未中文化**——文档/UI/客服都是英文
- MSB 在中国无分销渠道、无本地化服务

**修正后核心洞察**：力量举垂直在**中文市场**没有真正的双端原生 iOS 产品。这不是"全球无人做"，是"中文市场无人服务"——加上调研事实"100% 教练用表格 + 78% 用微信"——MeetPR 的机会窗口是中文市场速度。

[[../competitors/juggernaut-ai|JAI]] 走"AI 替代教练"路线，根本没有教练角色。中文市场也无 JAI。

### v4 反转（2026-04-27 议题 4 重新评估）

v0.7 议题 4 决议（v3）激进地把"多角色单用户"列为 V1 必做。v4 复盘后认为**V1 范围应回到 v0.5 的"一人一角色，注册后锁死"立场**：

- **V1 真实场景占比未知**：议题 4 决议时举的"肖天宇 = 教练 + 力量举学员"是 1 个数据点，不能代表 V1 公测人群规模化需求。Stage 1-4 内测/小公测人群（24 教练 + 30 自己练，~210-360 active）大概率**绝大部分只持一个身份**
- **V1 工程负担**：身份切换 tab + 跨身份数据隔离 + base profile 共享 + 推送/订阅按身份分流——单 dev 容易拖慢 B2B 核心闭环（议题 9 已确立 B2B 优先）
- **B2B 公测前 dogfood 即可验证**：肖+里欧本来就在内测全程深度使用，他们若有"自己也想训"需求，会以最低成本（注册第二个账号）告诉我们。先观察后再决定是否合并
- **数据模型 cleanup 的代价低**：V1 只用 `user.role: enum` 单值，V1.5 升级到 `user.roles: enum[]` 是一次 migration，不会因为 V1 简化而锁死未来

**触发 V1.5 多角色实施的条件**：

> B2B Stage 5-6 公测稳定后，实际用户反馈"教练自己也要训练"场景 ≥ 5 人（带具体场景描述，不只是"未来可能想要"），才启动 V1.5 多角色 epic。

## 决策（Decision）

### 业务架构（v1 不变）
- **双端**：教练 + 学员（v0.5 加自己练学员），都是一等公民
- **共享后端数据层 + 认证 + 订阅**
- **角色感知导航和 UX**：教练看学员面板/计划编排，学员看自己训练/成长
- **双向实时同步**：学员记录 → 教练立即可见；教练调整 → 学员立即收到

### 实现形态（v4：回到 v0.5 立场——单角色注册后锁死）

**单 iOS app + 单用户单角色（V1）**——明确否定"两个 iOS app 双 binary 双 listing"方案；同时**反转 v3 的"多角色 V1 必做"**。

**具体含义（V1）**：
- 1 个 Xcode target / 1 个 binary / 1 个 App Store listing
- 共享代码库（SwiftUI 组件 + Model 层 + Network 层 + 数据层）
- **三种身份**（v0.5 立场，v4 重新确认）：
  - 教练
  - 学员（有教练）
  - 学员（自己练）
- **角色选择时机（V1）**：注册时选教练 OR 学员，**之后不可切换**
- **学员"有教练 → 自己练"单向 mode toggle**：v0.5 设想的"自己练学员可从有教练→自己练单向切换"——**V1 不开放**，推迟到 V1.5 评估
- **教练 vs 学员注册后不可切换**：**V1 不开放**（v0.5 立场，v4 维持）；想换身份只能注销重新注册（与 v0.5 一致）

**V1.5+ 多角色升级 deferred**（v3 决议反转）：

> 以下 v3 设计**不在 V1 范围**，推迟到 V1.5+ 触发条件满足后再实施：
> - 主角色 = 教练 → 启用副身份"学员"
> - 主角色 = 学员 → "有教练 / 自己练"模式切换
> - 数据层 `user.roles: enum[]`（V1 用 `user.role: enum` 单值）
> - 账号设置里"切换身份" tab + 1-tap 切换
> - 每身份独立"我的"页 / 数据隔离 / base profile 跨身份共享
> - 典型场景：肖天宇 = 教练 + 力量举学员双身份
>
> **触发条件**：B2B Stage 5-6 公测稳定后，实际用户反馈"教练自己也要训练"场景 ≥ 5 人。

**ASO 策略**：App Store 描述需服务三类用户。建议主标题强调"力量举训练 + 教练-学员协作"，副标题三种用户场景轮播。

### 不做的选择

| 方案 | 为什么不选 |
|---|---|
| 学员端先做，教练端 V2 再加 | 没有教练端 = MeetPR 就是"又一个 MSB"，核心差异化丢失；且需要收教练钱但教练用不上 app，商业模式不成立 |
| 学员端 app + 教练端网页 | 调研显示 100% 教练用表格（网页）+ 微信（移动），**移动侧空白**才是机会；且教练回复学员经常在日常碎片时间，需要移动端 |
| **两个独立 iOS app 双 binary 双 listing** | v0.5 否决——2x 提审周期、2x 评论/崩溃跟踪、ASO 复杂度翻倍、跨端共享数据需服务端中转。单人开发负担过重 |
| 学员免费 + 教练付费跨平台方案 | 如 MSB 定价逻辑 — 但教练必须有工具才值得付费，不然钱从哪来？必须有教练端 |

## 理由（Rationale）

1. **用户调研证据**（[[../user-research|问卷]]）：
   - 教练 #1 需求 = **学员数据 + 视频自动归档**（加权 73 分）— 这是教练端功能，不是学员端
   - 教练 #2 需求 = **学员状态面板**（加权 63 分）— 纯教练端功能
   - 44% 教练对现状"将就能用"打 7-8 分 — 表格可用但需要主动切换的理由，**教练端体验**就是这个理由
   - 教练端功能价值排序第 1、2 都是只能在教练端实现的

2. **竞品真空**：
   - MSB 没教练端 → MeetPR 的教练端不需要打赢任何人，只需要做出来
   - JAI 无教练 → 完全不同赛道
   - 中文市场 + 力量举 + 双端：MeetPR 是第一家

3. **商业模式闭环**：
   - [[001-data-first-not-ai-first|ADR 001]] 确立收费方是教练（3-5% 学员计划费）
   - 教练愿意付费的前提是**教练自己用得爽** — 学员端 app + 教练用表格的方案，教练为什么要付我们钱？
   - 双端原生是收费合理性的基础

4. **战略护城河**：
   - 双端协作涉及大量 edge case（权限、同步、异常处理）— 做深了是壁垒
   - 数据沉淀双向流动（学员训练 → 教练分析 → 计划调整 → 学员执行），形成网络效应雏形

## 后果（Consequences）

### ✅ 好的方面

- 品类创新而非增量竞争，市场定位故事清晰
- 收费逻辑自洽：教练付钱 = 教练用工具 = 工具给教练省时间/赚钱
- 为后续双端特色功能铺路（教练批量操作、学员排队反馈、教练端 AI 助手等）
- **v0.5 单 app 决策的额外好处**：1 次 App Store 审核、共享代码库、共享更新节奏、共享 ASO 投入

### ⚠️ 需警惕

- **工程成本仍接近 2x**：两套 UI + 双向状态同步 + 权限隔离
  - 缓解：共享 SwiftUI 组件库、共享 Model 层、共享后端 API
- **双端同时打磨难度大**：MVP 必须两端都能用，不能一端完整一端残缺
  - 缓解：MVP 教练端可以功能面小但必须**闭环可用**（能编排 + 能看学员 + 能反馈）
- ~~**首版分发渠道要规划**：两个 app 还是一个 app？~~ **v0.5 已决策——单 app + 角色切换**
- **测试复杂度**：每个功能都要考虑两端状态 + 同步路径
  - 缓解：把"教练视角 / 学员视角"作为每个 feature 的 acceptance criteria
- **新增（v0.5）：单 app 的 ASO 挑战**——App Store 描述需要同时服务三类用户（教练 / 有教练学员 / 自己练学员），关键词分散
  - 缓解：主标题强 brand（MeetPR + 力量举），副标题轮播三类用户痛点
- **新增（v0.5）：单 app 的角色切换 UX**（v4 简化）
  - **V1**：教练 vs 学员注册后不可切换；学员"有教练 ↔ 自己练"也不可切换（v0.5 设想的单向切换 V1.5 评估）
  - **V1.5+ deferred（v3 议题 4 决议反转，v4 推迟）**：
    - 教练注册后可启用副身份"学员"（如肖天宇场景）
    - 学员注册后可启用副身份"教练"
    - 数据隔离：每身份独立"我的"页 / 训练记录 / 评估总结
    - 数据共享：base profile（手机号 / 头像 / 三大项 1RM）跨身份共享
    - 触发条件见 §背景 v4 反转

### 🧭 对后续 ADR 的约束

此决策是架构基石，以下决策都要在"单 app + 双端业务 + 单用户单角色（V1）"前提下做：
- **数据模型设计**：`user.role: enum`（**v4 反转回单值**，V1.5+ 触发后再升级到 `roles: enum[]`）+ role-aware data scoping
- 权限模型（V1：每个 user 一个角色，跨身份场景 V1.5+ 再考虑）
- 实时同步机制（WebSocket / polling / push）
- 订阅 / 付费流（教练按学员数 / 自己练学员订阅 / 家庭/团队套餐）
- ~~App 分发策略~~ **已决策——单 app**
- ~~身份切换 UX~~ **V1 不做**（V1.5+ 触发后再设计）
