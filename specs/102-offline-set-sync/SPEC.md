# 102 — 打勾先变绿：组记录本机排队、后台同步

- **状态**: Ready（2026-11-05 /grill 共识「确认」；顶部「待同步」条屏幕稿待「定稿」）
- **来源**: 学员反馈「网络不好的时候点完成 ✅ 要等很久」（2026-11-05 iOS 真机截图：坐姿哑铃推举第 2 组转圈、「全部按计划完成」变灰）。
- **范围**: 学员端今日训练卡，iOS（`MeetPR` 仓 `release/1.0`）与安卓 RN（`meetpr-rn` 仓 `main`）同批派卡、同批验收；两仓同目录镜像本文件。
- **级别 / 节奏**: T2 / P1。纯客户端，无后端、无数据模型改动（若实装中发现必须改后端，停下回报，不自行扩范围）。
- **相关**: spec 101（训练视频零丢失）同日确认，同样改「完成今日训练」的流程。两者的关系见 §2.4，两边实装要按那一节对齐。

## 北极星

**点了就算数。** 学员点 ✅ 的那一刻就是完成，不等网络。记录先存在手机里，有网就传，传不上就一直重试，不丢，也不让学员重点。

## 术语

**待同步（pending sync）**: 学员已经在手机上记下、但服务器还没确认收到的组记录（含勾选、取消勾选、改数、加组、删自加组、标未完成）以及「完成今日训练」。待同步的记录在界面上就当作已经生效。

## 现状（已核实，iOS `origin/release/1.0` 09eef51d / RN `origin/main` 6550369 / 后端 `origin/staging`）

- iOS：`TodayWorkoutViewModel.saveAccessoryRow` / `persist` 先 `await` 服务器返回才更新界面。等待期间 `accessorySavingIDs` 非空，**同一动作的其他组和「全部按计划完成」一起被禁用**。失败会把行回滚成原值。
- RN：`setsRepository.upsert`（`src/api/domains/sets.ts`）同样 `await`，30 秒超时。
- 后端 `POST /sets/log` 是按 `(student_id, plan_exercise_id, set_index)` 的**幂等 upsert**（`src/handlers/sets-log.ts`），重发同一组不会记成两条，后发的覆盖先发的。后端不拒绝往已完成的那天写组。是客户端的 `FlexibleTrainingDay.canWrite` 在完成后挡住写入。
- 「完成今日训练」走 `POST /plans/days/:dayId/complete`。iOS 已经是先放庆祝页、再等服务器确认（`completeDay(presentsCelebration:)`）。
- 视频要挂到组上，需要组的服务端 id（iOS `ensureLoggedSetID`、RN `video-upload/manager.ts` 都会先补写一次组）。

## 变更

### 1. 打勾立即生效（两端）
1. 点 ✅、取消勾选、改重量/次数/RPE、「加一组」、删自加组、标未完成、「全部按计划完成」：界面**立即**更新，休息倒计时立即开始，不出现转圈。
2. 任何一组在同步中，**都不禁用**同一动作的其他组和「全部按计划完成」。
3. 操作写进本机的同步队列（落盘，杀 app、重启手机不丢），后台按点的顺序依次发给服务器。同一组连续改多次，以最后一次为准（可以合并，也可以按序全发，后端是幂等 upsert）。
4. 发送失败（断网、超时、5xx）自动重试，退避节奏实装方定，有网络恢复信号时立即重试。**不回滚界面**，不弹错误。
5. 服务器明确拒绝且重试也没用的（4xx，除下面 §3 的情况）：这一条停止自动重试，进入「没传上」状态（§4 黄条），保留在队列里，等学员点重试。不删除，不回滚。

### 2. 「完成今日训练」排在队尾（两端，David 拍 1A）
1. 点「完成今日训练」：庆祝页照常**立即**出来；「完成」作为一条记录排在这天所有待同步组的**后面**，组全部送到之后才发完成请求。
2. 服务器收到的先后顺序和网好时一样，教练端看到的是完整的一天。
3. 庆祝页上需要服务器算的内容（如破 PR）：没同步完之前按手机上已有的数据显示，或者等同步完再补上。不允许因为没同步完而卡住庆祝页。
4. **与 spec 101 对齐**：当天有视频没送达时，按 101 的「等视频送达后完成」流程走（101 的「视频上传中 x/y」等待界面优先于本节的立即庆祝）。完成请求要等两个条件都满足：这天的组全部同步完，**并且**视频全部送达。两份 spec 的实装要共用同一个「完成闸门」，不能各写一个。
5. 待同步的组还没拿到服务端 id 时，学员点组号拍视频照常可以拍。视频进入 101 的上传流程，等这一组同步完拿到 id 再挂上去。不允许出现「先联网再拍」。

### 3. 教练改了计划（两端，David 拍 3A）
同步时服务器表示这条组记录对应的计划动作已经不存在（教练删了或换了动作）：把这一组按**自加动作**（spec 092）记到这一天，动作用原来的 `exercise_id`，组的数据原样保留。不丢，不提示学员，教练能看到。

### 4. 「待同步」提示（两端，David 拍 4A）
1. 只在今日训练页**顶部**挂一条：「{n} 组待同步，有网自动上传」。组行本身就是正常的绿勾，不加任何小标。
2. 队列清空后这条自动消失。
3. 有记录进入「没传上」状态（§1.5，或连续重试超过 30 分钟）：变成黄条「{n} 组没传上 · 重试」，点它立即重试全部。
4. 「完成今日训练」也在队列里时，计数只算组，不把「完成」算进 {n}。
5. 具体位置、颜色、间距以「定稿」屏幕稿为准。

### 5. 退出登录与换账号（两端，David 拍 2A）
1. 队列**按账号**存在本机。
2. 有待同步记录时点退出登录：弹窗「还有 {n} 组没上传」，两个按钮「先上传再退出」（显示进度，传完自动退出；传不完可以取消）和「直接退出」。
3. 选「直接退出」：队列不删，同一账号下次在这台手机上登录时自动接着传。换别的账号登录时不发、不显示上一个账号的队列。
4. 只有删掉 app 才会真的丢。换手机时没传的记录只在旧手机上，旧手机有网打开一次就会传上去。

### 6. 刷新与冷启动（两端）
1. 下拉刷新、切 tab 回来、冷启动拉到的服务器数据，要叠加本机的待同步记录再显示。**不允许**刷新后已勾的组变回没勾。
2. 冷启动有队列时立即开始同步。

## 文案（简中 / English；繁体走现有生成流程）

| 用途 | 简中 | English |
|---|---|---|
| 顶部条 | {n} 组待同步，有网自动上传 | {n} sets waiting to sync. They'll upload when you're online. |
| 失败条 | {n} 组没传上 · 重试 | {n} sets didn't upload · Retry |
| 退出弹窗标题 | 还有 {n} 组没上传 | {n} sets haven't uploaded yet |
| 退出弹窗按钮 | 先上传再退出 / 直接退出 | Upload, then log out / Log out now |
| 退出弹窗说明 | 直接退出也会保留，下次登录这个账号时接着传。 | They'll stay on this phone and upload next time you log in. |

（英文单复数按现有 i18n 规则；最终措辞以屏幕稿定稿为准。）

## 验收清单

1. 两端：开飞行模式，连点同一动作 4 组 ✅ → 每次点都立即变绿、休息倒计时立即开始，没有转圈，其他组和「全部按计划完成」都能点；顶部出现「4 组待同步」。关飞行模式 → 自动同步，顶部条消失；教练端/服务端能查到这 4 组，数据正确。
2. 两端：弱网（Network Link Conditioner / 模拟器限速，高延迟加丢包）下点 ✅ → 同上，立即生效。
3. 两端：断网打勾后杀 app，再断网冷启动 → 已勾的组仍是绿的，顶部条仍在；恢复网络后自动传上。
4. 两端：断网打完全部组后点「完成今日训练」→ 庆祝页立即出现；恢复网络后服务器先收到全部组、再收到完成，当天在服务器上是已完成，组数据完整。
5. 两端：同一组断网下先勾、再改重量、再取消勾选 → 恢复网络后服务器上是最后一次的状态。
6. 两端：断网打勾后，教练在网页把这个动作删掉 → 恢复网络后这几组作为自加动作出现在这一天，数据不丢。
7. 两端：后端对某条返回不可重试的 4xx（测试里注入）→ 顶部变黄条「{n} 组没传上 · 重试」，界面不回滚；点重试再次发送。
8. 两端：有待同步时退出登录 → 弹窗出现；选「直接退出」后用同一账号登回来 → 自动接着传；换另一个账号登录 → 看不到、也不会发上一个账号的记录。
9. 两端：待同步的组点组号拍视频 → 可以正常拍；联网后组先同步、视频随后挂到这一组上（与 101 一起验）。
10. 两端：当天有视频没送达时点「完成今日训练」→ 按 101 的等待流程走；视频和组都送达后才完成（与 101 一起验）。
11. **带历史的老用户升级后第一屏**：升级前已有的记录、已完成的天、正在传的视频，升级后显示不变，不重复，不丢；升级那一刻没有队列，行为与现在一致。
12. 两端：网络正常时，行为与现在一致（只是不再有转圈），服务器数据与改动前同样操作的结果一致。
13. 简中、英文、繁体各看一遍新文案；深浅色各看一遍。
14. 两端单测全绿；iOS 在 `iPhone 17e`、安卓在模拟器亲验 1、3–8 条并截图。

## 测试 seam

- **同步队列**：抽一个与界面无关的队列（iOS StudentKit 内，RN `src/features/training/` 下或 `src/api/domains/` 旁），注入「发送函数」「时钟」「网络状态」「存储」。在这一层测：顺序发送、失败重试不回滚、同一组合并、「完成」排在当天组之后、4xx 停止并标记、按账号隔离、落盘后重建队列。
- **叠加显示**：一个纯函数「服务器快照 + 待同步队列 → 界面行状态」，测刷新不回退、取消勾选、改数。
- **完成闸门**：与 spec 101 共用一个闸门（组全部同步 且 视频全部送达 → 发完成），在闸门层测两个条件的组合。
- **计划动作被删**：在队列的发送层注入「计划动作不存在」的错误，断言改成按自加动作写入。
- 优先复用现有 seam：iOS `TodayWorkoutViewModel` 的 repository 注入、RN `setsRepository` 的 mock（`src/api/domains/__tests__/repositories.test.ts`、`src/features/training/__tests__/completion-entry.test.tsx`）。

## Out of Scope

- 补记（spec 081 quick log）、身体状态填写（readiness）、聊天：本次不进队列，行为不变。
- 教练端（iOS 教练模式、plan-web）任何「学员有记录没同步」的提示。
- 后端改动、冲突合并规则改动（后端照旧是后写覆盖）。
- 完全离线使用：没网时首次打开 app、拉计划仍然需要网络；本 spec 只保证已经打开的今日训练里的操作不等网。
- 多台手机同时记同一天的冲突处理。
- 视频上传本身的可靠性（归 spec 101）。
